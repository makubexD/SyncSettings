The worker: headless Claude Code on DeepSeek

Opus writes the spec, then hands the typing to a second Claude Code process that talks to the paid DeepSeek API with your DeepSeek key. It has its own config folder, so it never sees your Claude login, hooks or plugins. Only the spec and the review use your Claude plan; the typing costs cents on DeepSeek.

You don't run any of this by hand. When a task is mechanical and has a plan, the main session sends it here and prints ⏵ mk-exec (deepseek deepseek-flash, medium effort): …. Effort defaults to medium: low = flash, light thinking; medium = flash, full thinking; high = v4-pro. Override per step with /mk-delegate --effort high … or tag the plan step [worker:high]. To make sure it gets used, run /mk-delegate, or turn on worker mode so Claude can't write the code itself.

Your controls

Commands and worker mode

Type these at the Claude Code prompt in any project. The ! commands run in your shell.

/mk-delegate [--effort low|medium|high] <task>Hands a task to the DeepSeek worker (default effort medium). Opus writes the spec, then reads the diff and reruns the tests before accepting. Works with a plan step too: /mk-delegate step 2 of docs/plan-x.md.
/mk-checkChecks the key (without showing it), the isolation from your Claude login and worker mode, then runs a 6-second live job on DeepSeek. The job itself uses no Claude tokens.
! workflow-report .After a feature: which steps went to the worker and which were done inline, every worker run with model, effort, exit, tokens and errors, and the commits.
! worker-mode onBlocks Claude from editing your code files, so every change goes through mk-exec. A green WORKER badge shows in the status line. Plan files and ~/.claude stay editable.
! worker-mode offLets Claude edit normally again. Use it for tiny fixes or judgment work.
! worker-mode statusShows whether it's on.

Any main model follows the delegation rule, including opusplan after you approve a plan. Without worker mode it relies on Claude following CLAUDE.md, and Claude must say so in one line before writing planned code itself. With worker mode on, it can't edit code files.

Step by step

Using it on real work

The pattern is always the same: Opus thinks and writes the plan, the DeepSeek worker types, Opus checks. Copy these prompts and swap in your own details.

  1. Start clean

    You, in the terminal

    Open Claude Code inside the project and clear old context. Commit or stash your changes first, because the worker needs a clean git tree.

    /clear /mk-check Is my git tree clean? If not, show me what's uncommitted.

  2. Ask Opus for a written plan

    Opus · spends usage, worth it

    This is the expensive thinking, and it happens once. Ask for exact files, exact changes and a test command, because that is what makes the work cheap to hand off.

    Plan adding pagination to the GET /users endpoint. Write the plan to docs/plan-pagination.md with small numbered steps. For each step list the files to change, the exact change, and the test command that proves it's done. Tag each step [worker] or [inline: reason], and list every test case with its expected result. Don't implement anything yet.

    Using plan mode or opusplan? That's fine. If the approved plan sends steps to the worker, Claude writes it to docs/plan-*.md and stops for your review instead of starting work. If every step is small and inline, your approval is the review and it goes ahead. For big work with several PRs or research first, ask for a roadmap of phases; each phase gets its own step-level plan when it starts.

  3. Read the plan yourself

    You

    Fix anything wrong now. A mistake in the plan is cheap to fix here and costly once code exists. Check the tags too: a test step whose cases are all listed can go to the worker. When it looks right, commit the plan and clear, so execution doesn't carry the planning context.

    Step 3 should use cursor pagination, not offset. Step 1 lists every test case, so tag it [worker]. Update the plan and commit it.
    /clear

  4. Hand a step to the worker

    mk-exec → claude -p → DeepSeek · cents

    The command sends the step to the DeepSeek worker and Opus reviews the result. You should see a ⏵ mk-exec … line. Add --effort high for a harder step. One step at a time keeps each diff easy to review. To be sure Claude doesn't write it itself, run ! worker-mode on first.

    /mk-delegate step 1 of docs/plan-pagination.md

  5. Let Opus check the result

    Opus · review gate

    Opus reads the diff and reruns the tests on its own. Ask to see the evidence when you want it.

    Show me the diff and the test output for that step. Did it touch anything outside the plan?

  6. Accept or reject

    You decide

    Accepted work gets committed. A rejection with a concrete reason goes back to the worker once. A second failure means Opus does it directly.

    Looks good. Commit it with a short message. /mk-delegate step 2 of docs/plan-pagination.md
    Reject: it changed the response shape of /users. Resend step 1 to the worker and say the JSON fields must stay the same.

  7. Finish and clear

    You

    When the plan is done, look at the run report, get one final review, then start the next feature in a fresh session.

    All steps are done. Run workflow-report on this repo and tell me which steps ran inline and why, then review the whole feature with /agent-skills:review and summarize what changed.

Which tasks go where

Send to the worker

  • “Rename getUser to fetchUser across src/ and update imports and tests.”
  • “Add docstrings to every public function in utils/.”
  • “Convert the 12 test files in tests/ from Jest to Vitest, following docs/plan-vitest.md.”
  • “Add a --verbose flag to cli.py exactly as described in spec.md.”

Keep on Opus

  • “Why does login fail only on Safari?”
  • “Design the database schema for teams and roles.”
  • “Review this branch for security problems.”
  • Anything without a plan yet. Plan it first.
  • Evals and probes of how a model behaves. The worker is DeepSeek, so it would measure DeepSeek. It can still write the eval files.

Never send to the worker

  • Anything that needs .env, API keys or passwords.
  • Private or customer data.
  • Work outside a git repo, or on a dirty tree.

Quick template for any handoff:

/mk-delegate <the exact change>. Files: <list>. Done when: <test command> passes. Don't touch any other file.

What spends your plan usage

Spends usage

  • Every message and tool result in the main session. The whole conversation is re-read each turn, so long sessions get pricier per turn.
  • Each Claude subagent (Explore, Plan, reviewers). It starts cold and rebuilds context you already had.
  • Big file reads and pasted logs that land in context.
  • High, xhigh and max effort: more thinking per answer.
  • Multi-agent reviews like /code-review max or ultra.

Free, or saves usage

  • The DeepSeek worker. It costs cents on your DeepSeek balance, not plan usage, and only its short summary comes back.
  • Shell output RTK trims away before it reaches context.
  • Data processed inside ctx_execute. Only what it prints enters the conversation.
  • Prompt cache hits. Staying on one task keeps the cache warm.
  • /clear: a fresh session re-reads nothing.

Effort routing

Default is medium. Effort goes up one tier when the output misses the bar, before switching models.

EffortUse it forWho usually runs it
lowMechanical work with a clear spec: formatting, bulk edits, migrationsmk-exec on DeepSeek (its own effort: default medium)
mediumRoutine implementation, searches, straightforward fixesMain session, Explore
highDebugging, design, reviews, cross-cutting refactorsMain session (Opus)
xhigh / maxAdversarial checks, judge panels, gnarly root causesOpus, only when you ask

Habits that keep usage low

  • Run /clear between unrelated tasksOld context gets re-read on every turn. A new task rarely needs it. Use /compact when one task runs long.
  • Ask for a plan firstA written plan or spec is the ticket to the worker. Without one, the work stays on Opus.
  • Work in a clean git repomk-exec needs a clean tree so its diff is easy to review. Commit or stash before mechanical jobs.
  • Point at files, don't paste themGive a path or a log file. context-mode can index and search it instead of loading the whole thing.
  • Stay at medium effortAsk for high only for debugging or design. Ask for max or ultra reviews only when the stakes are real.
  • Watch the ⏵ linesEach one is a spawn. A fan-out of many agents on a small task is a sign to stop and redirect.
  • Say "do it inline"For small jobs, a subagent costs more than doing the work in the main session.
  • Glance at the status lineIt shows session cost, context used and cache reads. Context past about 60% is a good moment to compact or clear.

Guardrails that protect your account

Anthropic's consumer terms allow your subscription login only in Claude Code and Claude.ai. Breaking these can get the account banned.

  • Never connect Anthropic or Claude inside OpenCode (/connect, opencode-anthropic-auth) or OmniRoute.
  • Never set ANTHROPIC_BASE_URL on your main Claude Code session. Only the mk-exec child process gets the DeepSeek endpoint, with its own config folder ~/.claude-worker.
  • Never send secrets, .env files or private data through the worker. The paid DeepSeek API is not zero-retention.
  • Keep the DeepSeek key only in ~/.config/claude-workers/env (mode 600).
